## 1. 패키지 레이아웃 — `common/` 은 주제별, 모듈은 계층별

파일이 한 폴더에 평평하게 쌓이면 "이게 배선인지 도메인 커널인지 유틸인지"를, 모듈 안에서는
"이게 HTTP 경계인지 유스케이스인지 영속인지"를 **파일 이름으로만 추측**해야 한다. 이름은 규칙이
아니라 관습이라 어긋나도 아무도 못 막는다. **폴더로 묶어 컴파일러가 보이게 만든다**:

```
com.recall
├── common/               # 리프 — 기능 모듈을 참조하지 않는다
│   ├── config/           #   배선: 시큐리티 체인 · CORS · 호출자 식별
│   ├── exception/        #   ErrorCode + 예외 타입 + 전역 핸들러 하나
│   ├── web/              #   응답 형식: ApiResponse · ApiError · 헬스 엔드포인트
│   ├── type/             #   유형 확장 커널: MemoryType · TypeStrategy · StrategyRegistry
│   ├── prompt/           #   프롬프트 리소스 로딩 · LLM 응답 취급 유틸
│   └── secret/           #   자격증명 암·복호화 · 로그 마스킹
└── <domain>/             # 모듈 = 한 도메인 (capture · memory · review · query · store · search · settings)
    ├── (root)            #   공개 계약: 다른 모듈이 import 하는 것만 (예: CaptureCreatedEvent)
    ├── controller/       #   HTTP 변환만
    │   └── dto/          #     요청·응답 record — 이 모듈의 HTTP 계약
    ├── service/          #   유스케이스 · 트랜잭션 · 도메인 협력자
    │   └── entity/       #     JPA 엔티티 · VO · 상태 enum
    ├── repository/       #   영속 (Spring Data · 네이티브 쿼리 스토어)
    ├── config/           #   이 모듈이 소유한 빈 배선 (예: 전용 executor)
    └── type/             #   유형별 전략(SPI) — 유형이 변동 축인 모듈만
```

- **폴더는 개수가 아니라 종류로 쪼갠다.** 같은 종류 파일이 한 폴더에 여러 개 있는 건 목록이고 읽기 쉽다.
  읽는 비용을 만드는 건 **종류가 섞인 폴더**다 — 유스케이스 옆에 시큐리티 배선, 그 옆에 암호화 유틸.
- **`common` 에 도메인 로직·엔티티·리포지토리를 두지 않는다.** 배선과 공유 커널만.
- 계층 방향은 `controller → service → repository` 한 방향. 역방향·횡단 호출 금지.

### 모듈 root = 공개 계약

모듈 root 에는 **다른 모듈이 실제로 import 하는 것만** 둔다. 나머지는 전부 계층 폴더 안이다.

> **왜** — "이 모듈의 공개 API가 무엇인가"는 평평한 패키지에서 **답할 방법이 없다.** 모든 클래스가
> 같은 층에 있으니 엔티티·리포지토리·내부 협력자가 유스케이스와 구별되지 않고, `public` 하나로
> 모듈 밖에 그대로 노출된다. root 를 공개 계약으로 비워 두면 **경계 침범이 import 문에 드러난다** —
> 남의 `service.entity` 나 `repository` 를 import 하는 줄은 그 자체로 위반의 증거다.

- **`XxxServiceImpl` 껍데기를 만들지 않는다** — 계층 폴더는 두지만 `service/impl/` 은 두지 않는다.
  구현체가 하나뿐인 인터페이스는 간접층만 늘린다(`backend/CLAUDE.md`: 포트는 교체가 실제로 필요한
  경계에만). 인터페이스가 정당한 곳은 `llm/` 의 `LlmClient`·`EmbeddingClient` 뿐이다.
- **`llm/` 은 이 레이아웃에서 빠진다** — 컨트롤러·엔티티·리포지토리가 없는 **포트/어댑터 모듈**이다
  (root = 포트와 팩토리, `provider/<vendor>/` = 어댑터). 계층 폴더를 억지로 씌우면 빈 폴더만 생긴다.
  레이아웃은 규칙이지 의식이 아니다 — 층이 없는 모듈에 층을 그리지 않는다.
- **테스트는 대상과 같은 패키지에 둔다.** 단위 테스트는 대상 클래스를 따라 계층 폴더로 들어가고,
  여러 층을 지나는 시나리오·격리 테스트는 모듈 root 에 남는다.
- **모듈 간에는 record 를 주고 JPA 엔티티를 주지 않는다.** 다른 모듈이 쓸 값은 root 의 record 로 낸다
  (예: `memory/StoredMemory`).

  > **왜**: 엔티티는 가변이고 영속 컨텍스트에 묶여 있다. 남의 모듈에 넘기면 세터로 상태가 바뀔 수 있고,
  > dirty checking 이 언제 flush 되는지가 호출자 코드에 없는 곳에서 결정되고, 트랜잭션 밖에서 lazy 필드를
  > 만지면 터진다. 계약은 **필요한 필드만** 담는다 — 넓혀 두면 그만큼이 못 바꾸는 약속이 된다.

- **남의 리포지토리를 직접 잡지 않는다.** 테이블을 소유한 모듈의 공개 계약을 통한다.

  > **왜**: 같은 테이블에 쓰는 경로가 둘 생기면 저장 규약도 둘이 된다. 실제로 승인이 `new Memory(...)` 를
  > 직접 만들어 저장하고 있었고, 그 상태에서 memory 쪽에 불변식을 추가하면 **승인으로 만들어진 행만**
  > 규약을 벗어난 채 쌓인다. 게이트를 지키는 코드와 게이트에 넣는 코드가 다른 모듈에 있으면 그 게이트는
  > 규칙이 아니라 관습이다.

- **인덱스·부수 테이블은 그것을 쓰는 모듈이 소유한다.** `memory_embedding`·`search_tsv` 를 다루는 저장소는
  `search` 안에 있고, 색인 절차도 거기 있다(`search/SearchIndex`).

  > **왜**: 저장소가 memory 에 있던 동안 승인 경로와 재색인 경로가 **각자** 표현을 조회해 임베딩을 저장했다.
  > 절차가 복제되면 "색인 텍스트에 무엇을 넣는가"를 한쪽만 바꿔도 같은 카드가 승인 직후와 재색인 이후에
  > 다르게 검색된다.

- **모듈 경계를 넘는 FK 는 연관(`@ManyToOne`) 이 아니라 id 컬럼으로 맵핑한다.**

  > **왜**: 연관으로 두면 그 모듈이 남의 **엔티티 클래스**를 알아야 하고, 그 지식이 엔티티에서 그치지 않고
  > 행을 만드는 서비스까지 번진다(참조를 얻어야 하므로). 필요한 건 FK 값 하나이고 **무결성은 DB 제약이
  > 지킨다**(스키마는 Flyway 소유). 값으로 낮추면 lazy 프록시·연관 탐색이 사라져 트랜잭션 밖 접근 사고도
  > 없어진다. 대가는 `a.getB().getC()` 탐색을 못 하는 것 — 그건 B 의 공개 계약에 물어본다.
  >
  > **주의**: 연관이 강제하던 불변식이 있으면(예: `Memory.user_id` 는 capture 소유자여야 한다) 값으로
  > 낮추는 순간 그 강제가 사라진다. 그때는 **유일한 쓰기 경로가 그 파생을 책임지고, 회귀 테스트가 타입의
  > 자리를 대신한다**(`MemoryAccessOwnerDerivationTest`).

- **테스트를 위해 프로덕션 가시성을 넓히지 않는다.** package-private/protected 멤버가 필요하면
  **테스트 소스 루트에 같은 패키지의 픽스처**를 두어 닿는다(예:
  `test/…/settings/service/entity/ModelSettingFixture`). 생성자를 `public` 으로 올리는 건 테스트
  편의를 위해 프로덕션 API 를 여는 것이다.

## 2. 컨트롤러 — 반환은 공통 응답 형식 하나

- **모든 REST 컨트롤러는 `ApiResponse<T>` 를 반환한다.** 성공은 `{success:true, data}`,
  실패는 `{success:false, error}`. 돌려줄 값이 없는 동작(반려·상태 전이)도 `ApiResponse.ok()` 다.

  > **왜**: 전에는 성공이 원본 DTO, 실패는 RFC 7807 `ProblemDetail` 이었다. 형태가 비대칭이면
  > 호출자가 **본문을 파싱하기도 전에 상태 코드로 먼저 갈라야** 하고, 화면·어댑터·테스트가 각자 그 분기를
  > 다시 만든다. 실제로 프론트 `client.ts` 는 공통 `request()` 를 갖고도 `updateSettings` 만 fetch 를
  > 따로 열어 `ProblemDetail.detail` 을 뽑고 있었다 — 같은 분기의 두 번째 사본.

- **유일한 예외는 SSE**(`POST /api/query`). 응답이 하나의 JSON 본문이 아니라 조각의 흐름이라
  조각마다 공통 형식을 씌우면 프레임이 배로 늘고 소비 코드가 매 조각에서 `success` 를 다시 본다.
  새 예외를 만들려면 이 문서에 이유와 함께 추가한다.
- **컨트롤러는 HTTP 변환만 한다.** 소유자 스코프·권한·상태 검증·404 은닉은 서비스가 판정하고,
  예외 → 응답 변환은 전역 핸들러 한 곳이 한다. 컨트롤러에 `try-catch` 를 두지 않는다.
- **상태 코드는 `@ResponseStatus` 로 선언한다.** `ResponseEntity` 를 손으로 조립하면
  본문 타입이 공통 형식인지 원본인지 시그니처만 봐선 알 수 없다. `ResponseEntity` 는 상태가
  런타임에 갈리는 경우(전역 핸들러)에만.
- **엔티티를 반환하지 않는다.** 응답은 `dto/` 의 record 로 변환해서 낸다.

## 3. 예외 — 종류별 타입 + 코드 열거 + 핸들러 하나

- **`ErrorCode` 열거가 코드와 HTTP 상태의 유일한 정의다.** 상태를 예외 타입이 아니라 코드가 들고 있다.

  > **왜**: 예외 타입과 코드가 각자 상태를 정하면 둘이 어긋난다. 그리고 클라이언트가 분기할 수 있는
  > **안정된 식별자**가 없으면 화면이 한국어 메시지 문자열을 비교하게 된다.

- **도메인 예외는 `ApiException` 하위 타입으로 던진다.** 현재 종류:

  | 예외 | 코드 | 상태 | 언제 |
  |---|---|---|---|
  | `ValidationException` | `VALIDATION_ERROR` | 400 | 요청 값의 형식·범위 위반 |
  | `NotFoundException` | `NOT_FOUND` | 404 | 없는 리소스 **또는 남의 리소스**(존재 은닉) |
  | `ConflictException` | `CONFLICT` | 409 | 현재 상태와 모순되는 요청 |
  | `AiNotConfiguredException` | `AI_NOT_CONFIGURED` | 409 | chat/embedding 미설정 상태에서 그 기능 요구 |
  | `NotImplementedException` | `NOT_IMPLEMENTED` | 501 | 골격만 있는 단계 |
  | `UpstreamUnavailableException` | `UPSTREAM_UNAVAILABLE` | 502 | 외부 provider 무응답·5xx |

- **"내 입력이 잘못됐다"와 "상류가 고장났다"를 하나로 뭉개지 않는다.** 사용자가 할 일이 정반대다.

  > **왜**: 설정 저장 전 임베딩 프로브가 provider 의 **모든** 실패를 400 `VALIDATION_ERROR` 로 바꾸고 있었다.
  > provider 가 잠깐 죽은 동안 정상 설정을 저장하려는 사용자에게 **"키·모델을 확인하라"고 틀린 안내**를 하고,
  > 상류 장애가 4xx 로 기록돼 **5xx 모니터링에서 사라졌다.** 기준: provider 가 4xx 로 답했으면 내 입력 문제(400),
  > 5xx·연결 실패·분류 불가면 상류/서버 문제(502).

- **`IllegalStateException`·`IllegalArgumentException` 을 HTTP 경계까지 올리지 않는다.**
  호출자가 고칠 수 있는 상황이면 위 타입 중 하나로, 내부 배선 버그면 그대로 500 으로 둔다.

  > **왜**: 이 둘은 "내부 불변식 위반"과 "호출자 입력 오류"를 같은 타입으로 표현한다. 전에
  > `IllegalArgumentException → 400` 규칙이 있었는데, 그 규칙이 **내부 배선 버그(등록된 전략 없음)까지
  > 400 으로 감췄다.** 반대로 `ReviewService` 의 "이미 처리된 검토 항목"은 `IllegalStateException` 이라
  > catch-all 에 걸려 **500** 으로 나갔다 — 호출자가 고칠 수 있는 상황이 서버 장애로 보고됐다.

- **격하(fallback)의 catch 범위는 전용 예외 타입으로 좁힌다.** "실패하면 이 한 건을 건너뛴다"는 장치가
  `RuntimeException` 을 잡으면 **범위가 다른 실패까지 같은 신호가 된다.**

  > **왜**: `CardCodec.readOrNull` 은 값 모양이 어긋난 행 한 건을 건너뛰기 위한 격하인데, `RuntimeException`
  > 을 잡으면서 **"이 유형에 전략이 등록되지 않았다"(배선 결함)까지 `null`** 로 만들었다. 두 실패의 범위가
  > 다르다 — 앞은 그 한 건이고 뒤는 **그 유형의 모든 카드**다. 그 결과 재색인이 그 유형의 임베딩을 전부
  > 지우고도 잡을 `READY` 로 마쳤다(벡터 채널은 정상으로 표시된 채 그 유형이 검색에서 사라진다).
  > 격하 대상은 `CardUnreadableException` 처럼 **전용 타입**으로 좁히고, 실패 원인을 만드는 조회는
  > `try` 밖에 둔다.

- **전역 핸들러(`@RestControllerAdvice`)는 하나.** 프레임워크 예외도 개별 핸들러로 끌어낸다:
  타입 불일치·매핑 없는 경로·읽을 수 없는 본문·미지원 메서드는 모두 4xx 인데, 핸들러가 없으면
  맨 아래 `Exception` 핸들러가 붙잡아 **500** 으로 나간다.
- **catch-all(500)에 도달한 예외는 그 자체가 결함**이다 — 분류되지 않았다는 뜻이므로, 로그를 보고
  위 표에 넣거나 개별 핸들러를 추가한다.
- **`traceId` 는 추적돼야 한다.** 에러 응답의 `traceId` 를 서버 로그에 같이 남긴다.
  사용자가 보고할 수 있지만 아무도 로그와 상관시킬 수 없는 식별자는 있으나 마나다.
- **에러 응답은 컨텐츠 협상 대상이 아니다.** 전역 핸들러는 `Content-Type: application/json` 을 못 박아
  응답한다. 요청이 무엇을 받겠다고 했든 실패 사실은 전달돼야 한다.

  > **왜**: 응답 객체를 그냥 반환하면 스프링이 요청 Accept 와 협상하고, 실패하면 `HttpMediaTypeNotAcceptable`
  > 이 **핸들러 안에서** 터진다. 이미 예외 처리 중이라 다시 잡히지 않아 원 예외가 재전파되고 클라이언트는
  > **500 + 빈 본문**을 받는다. 실제로 SSE 소비자(`Accept: text/event-stream`)에게 409 `AI_NOT_CONFIGURED`
  > 와 400 검증 실패가 모두 빈 본문으로 나갔다 — 구 핸들러의 `ProblemDetail` 에는 프레임워크 폴백이
  > 있었고 공통 형식으로 바꾸면서 사라진 것이다.
- **응답에 내부 정보를 싣지 않는다.** 파서 메시지·기대 타입·클래스 이름·자격증명 금지.
  필드 **이름**은 알려 줘도 된다(값이 아니므로).
- **응답이 이미 커밋됐으면 아무것도 쓰지 않는다.** SSE 타임아웃처럼 스트림이 시작된 뒤 터지는 예외는
  헤더·본문을 더 쓸 수 없다 — 응답을 쓰려는 시도 자체가 다시 실패한다. `null` 을 반환해
  "처리했고 쓸 것은 없다"를 알리고 사실은 로그로 남긴다(삼키는 게 아니라 통로가 닫힌 것).

  > **검사는 개별 핸들러가 아니라 응답을 만드는 공통 통로에 둔다.** 조건 없는 규칙을 핸들러마다 손으로
  > 지키면 **새 핸들러에서 빠뜨린다.** 실제로 async 타임아웃 핸들러에만 검사가 있었고 catch-all 에는
  > 없어서, 스트리밍 중 터진 비-타임아웃 예외(근거 전송 실패 → `completeWithError`)가 커밋된 응답에
  > 500 본문을 쓰려 했다. 모든 에러 응답이 지나는 한 곳에서 막으면 규칙이 **구조적으로** 성립한다.

### 대소문자·로케일

- **열거값·provider 이름 등 토큰 정규화는 `Locale.ROOT` 로 한다.** 기본 로케일 `toUpperCase()`/
  `toLowerCase()` 금지.

  > **왜**: 터키어 로케일에서 `i → İ` 로 올라간다. `anthropic`·`openai`·`RESOLVED` 처럼 `i` 를 담은
  > 토큰이 매칭에 실패해 **모든 카드가 조용히 `UNRESOLVED` 로 격하되고 provider 조회가 전부 빈다.**
  > 한 곳(`MemoryTypeMatch`)만 이 규칙을 지키고 나머지 7개 파일이 기본 로케일이었다.

## 4. `Map` 을 계약으로 쓰지 않는다

- **응답·요청 타입으로 `Map` 금지.** 타입 있는 record 를 만든다.

  > **왜**: `Map.of("status","ok","service","recall")` 에서 키 이름이 계약인데 컴파일러가 지켜 주지
  > 않고, 응답 스키마가 코드에서 읽히지 않아 프론트가 무엇을 받는지 알려면 구현을 열어야 한다.
  > 실제로 있었던 것: `Map<String,String> health()`, `Map<String,Long> count()`,
  > `Map<String,Long> approve()`, `Map<String,String> reject()`.

- **모듈 경계를 넘는 데이터도 `Map<String,Object>` 로 넘기지 않는다.** 타입 있는 계약을 만든다.

  > **왜**: 카드 구조화 필드가 SPI 경계에서 `Map<String,Object>` 였을 때, 만드는 쪽(유형 전략)과 읽는
  > 쪽(memory·review·query·search 모듈)이 **같은 필드 이름을 각자 문자열로 다시 적었다.** 카드 필드
  > 이름을 바꿔도 컴파일 에러가 0개 나고 런타임에 조용히 빈 값이 됐다. 값 타입도 안 지켜져 읽는 쪽마다
  > `instanceof List<?>` 방어를 다시 썼다.

- **`Map` 이 남아도 되는 자리**는 둘뿐이고, 그 이유가 코드에 적혀 있어야 한다:
  ① 유형과 무관하게 카드 전체를 클라이언트로 실어 보내는 자리(`MemoryDetailResponse.structured`),
  ② **스키마를 몰라야** 동작하는 자리(S3 결정론 병합). 나머지는 타입으로 바꾼다.
- 스키마리스 저장(JSONB) ↔ 타입 변환은 **한 곳**(`CardCodec`)에서만 한다. 클래스마다
  `new ObjectMapper()` 를 두면 되읽기가 스키마 정규화를 건너뛴다(실제로 긴맥락 병합 경로가 그랬다).

## 5. 반복되는 문자열은 소유 도메인이 상수로 갖는다

- **같은 문자열이 두 곳 이상에 나오면 상수로 뺀다.** 두는 자리는 **그 어휘를 소유한 도메인 패키지**다.
  거대한 `Constants` 클래스 하나에 모으지 않는다 — 그러면 모든 모듈이 그 클래스에 의존한다.

  현재 어휘와 소유자:

  | 어휘 | 소유 | 형태 |
  |---|---|---|
  | memory 수명 상태 (`active`·`archived`·`incorrect`) | `memory/MemoryStatus` | String 상수 |
  | 검토 상태 (`pending`·`approved`·`rejected`) | `review/ReviewStatus` | String 상수 |
  | capture 처리 상태 (`PROCESSING`·`DONE`·`FAILED`) | `capture/CaptureStatus` | String 상수 |
  | 임베딩 인덱스 상태 (`READY`·`REINDEXING`·`FAILED`) | `settings/EmbeddingStatus` | String 상수 |
  | 임베딩 kind (`problem`·`solution`·`document`·`fact`) | `memory/type/EmbeddingKind` | String 상수 |
  | 융합 채널 | `memory/type/SearchChannel` | **enum** |
  | 카드 필드 이름 | 카드 record 자체(접근자) | 문자열로 적지 않는다 |

- **닫힌 집합은 enum, 열린 집합은 String 상수.**
  - 채널은 enum이다: 채널 추가는 검색기에 질의 경로를 만드는 일이라 공유 코드가 반드시 바뀐다.
    그리고 문자열 키였을 때 `RrfFusion.getOrDefault(1.0)` 이 오타를 **조용히 삼켜** 유형별 가중치
    설계가 무효화됐다(로그도 없었다).
  - 임베딩 kind는 String 상수다: "새 지문 종류 = 행 추가로 끝"(architecture.md 가드레일 3)이므로
    닫힌 enum을 공유 코드에 두면 새 유형이 공유 코드를 고쳐야 해 OCP가 깨진다.
  - DB 컬럼이 `VARCHAR` 이고 JPA·native SQL·`@RequestParam` 경계가 문자열을 그대로 쓰는 상태값도
    String 상수로 둔다(enum으로 올리면 그 세 경계에 변환을 새로 깔아야 한다).
- **같은 문자열이 여러 네임스페이스에 사는 것을 경계한다.** `"document"` 는 ① 카드 필드 이름,
  ② 임베딩 kind, ③ Voyage API input type 으로 **동시에** 쓰이고 있었고, 무엇도 셋을 구분하지 않았다.
  상수로 올리면 어느 네임스페이스를 의도한 것인지 코드가 말한다.
- **테스트가 프로덕션 문자열을 복사해 두지 않는다.** 프로덕션 상수를 참조하거나 타입으로 고정한다.
  복사해 두면 프로덕션 이름을 바꿔도 테스트는 통과하고 동작만 조용히 격하된다(실제로 그랬다).

## 6. 테스트 — 신호 없는 테스트는 만들지 않는다

- **테스트하지 않는 것**: getter/setter, `supports()` 처럼 한 줄 `return` 하는 위임,
  **테스트가 자기 리터럴을 검증하는 것**(손으로 적은 리스트의 `size()`), 부작용 없는 순수 함수를
  여러 번 호출해 "같은 결과가 나온다"고 확인하는 동어반복.

  > 실제로 지운 것: 전략 7개의 `supports()` 테스트, 손으로 적은 5개 리스트의 길이를 확인하던
  > "SPI 커버리지" 테스트(리스트가 손으로 적혀 있으니 누락을 애초에 못 잡는다 — 실제 보장은
  > `StrategyRegistry` 가 부팅·디스패치에서 한다), `RrfFusion` 을 5번 호출하던 결정론 테스트.

- **테스트할 것**: 결정론 단계(마스킹·플래너·검색·융합·병합)는 순수 함수 단위테스트,
  확률적 단계(분류·추출·판정·리랭크·답변)는 **파싱·정규화·격하 경로**를 포트 뒤의 fake 로 고정.
- **🔴 치명 케이스는 회귀 테스트 필수**: 마스킹 유출, 충돌 자동 덮어쓰기, 근거 없는 생성,
  소유자 교차유출. `@Tag("release-gate")` 로 표시한다.
- **버그를 고치면 그 버그를 재현하는 테스트를 남긴다** — 고친 사실이 아니라 **깨지던 조건**을 고정한다.

## 7. 이 문서를 고치는 규칙

규칙을 바꿀 때는 **어떤 실패를 봤는지**를 함께 적는다. 근거 없이 적힌 규칙은 다음 사람이
지울 수도, 지키지 않을 수도 없다. 되돌리기 어려운 선택(임계값·가중치·계약 형태)은
`docs/setup.md` Decision Log 에도 한 줄 남긴다.
