# recall-feature — PRD 기반 기능 개발

Recall의 기능은 "무엇이 일어나야 하는가(결정론)"가 아니라 **"어떤 출력이 받아들여질 만한가(범위)"**
로 정의된다. 이 스킬은 새 기능/파이프라인 단계를 **PRD 근거 → 원칙 검증 → 경로에 배치 → Eval**
순서로 붙이도록 강제한다.

## 0. 먼저 읽는다

1. **Recall AI PRD** (`docs/recall_ai_prd.md`). 특히 해당 기능이
   속한 단계의 §. 없으면 사용자에게 PRD 위치를 묻는다 — PRD 없이 기능을 지어내지 않는다.
2. 루트 `CLAUDE.md`의 **불변 원칙**과, 작업 영역(`backend`/`frontend`/`nginx`)의 CLAUDE.md.

## 1. 단계 성격을 먼저 정한다 (🔵 LLM / 🟢 결정적)

기능이 PRD의 어느 단계인지, 성격이 무엇인지 확정한다. **성격이 배치와 Eval 방식을 정한다.**

| 경로 | 단계 | 성격 |
|------|------|------|
| 조회 | Query Classifier(C) | 🔵 LLM |
| 조회 | Search Planner(P) / Hybrid Retriever(R) / Weighted Ranker(W) | 🟢 결정적 |
| 조회 | Reranker(RR) / Answer Composer(A) | 🔵 LLM |
| 저장 | 마스킹(M0) | 🟢 패턴(LLM 이전) |
| 저장 | 구조화 추출(S2) / 긴맥락 Map-Reduce(S3) / 유사·모순 판정(S4) | 🔵 LLM |

- **🟢 결정적 단계에 LLM을 넣지 않는다**(재현·감사·비용). P/R/W는 라우팅표·순수함수로.
- 🔵 LLM 단계는 **structured output(function calling/JSON 스키마)을 강제**하고, 낮은 확신도는
  단정 대신 confidence로 표현한다.

## 2. 불변 원칙 게이트 (하나라도 어기면 멈춘다)

- [ ] 이 기능이 **memory에 자동으로 쓰지 않는가?** (저장은 반드시 검토 대기 → 승인 경유)
- [ ] 원문이 외부 LLM/인덱스/로그로 나가기 전에 **마스킹이 선행**하는가?
- [ ] 삭제 대신 **상태 전이**로 처리하는가? 충돌을 자동 덮어쓰지 않는가?
- [ ] 결정적이어야 할 단계에 LLM을 몰래 끼워 넣지 않았는가?
- [ ] 답변/결과가 **저장된 근거에 매여** 있는가? 근거 없으면 "기록 없음"인가?
- [ ] 실패·부분성공·절단을 **상태로 노출**하는가? (조용한 실패 금지)

## 3. 경로에 맞게 배치한다

- **저장 경로**: 원문 커밋만 동기(유실 금지 앵커) → 마스킹·추출·판정은 `@Async` 잡 → 결과는
  검토 대기(pending)로만. 부분 결과를 memory/검토함에 남기지 않는다(실패 시 롤백, 원문 보존 재시도).
- **조회 경로**: 동기 SSE. LLM 호출은 분류+답변으로 최소화(그 사이는 결정적). 각 단계는 앞 단계
  없이도 **격하 동작**(graceful degradation): C 실패→broad hybrid, RR 실패→W 결과 그대로,
  A 실패→검색 카드+근거 그대로.

## 4. 임계값·가중치는 라벨셋에서 fit (직관 금지)

`τ_conf·τ_recall·τ_sim·τ_ans`·채널 가중치·boost/penalty는 **매직 넘버가 아니다**. 초기값은
시작점일 뿐, Eval 라벨셋에서 측정·조정하고 회귀로 지킨다. 계수를 바꾸면 근거를 커밋/Decision Log에.

## 5. Eval을 같이 만든다 (PRD의 심장)

기능만 만들고 끝내지 않는다. 해당 단계의 Eval 케이스를 추가한다.

- 🟢 결정적 단계 → **순수함수 테스트**(라벨→기대 plan 100% 일치, 미정의 조합=폴백+로그).
- 🔵 LLM 단계 → 라벨셋 지표(Recall@k/nDCG) 또는 LLM-as-a-Judge(근거 일치·형식·faithfulness).
- 🔴 치명 케이스(민감정보 유출·충돌 자동 덮어쓰기·근거 없는 생성)는 **릴리스 차단 게이트**로 반드시 포함.
